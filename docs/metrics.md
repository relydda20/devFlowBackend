# Productivity Metrics & ETL

Two productivity-wellness metrics are derived from the raw telemetry in `activities`: **code churn** and **context switching**. A periodic ETL job rolls these up into two small aggregate tables that the future dashboard reads.

## What the metrics measure

### Code churn (`typing-heuristic`)

`churn_ratio = min(1, total_lines_deleted / total_lines_added)` over the requested date range.

- `lines_added` and `lines_deleted` are **typing-level**, derived from each `text_change` event's `affected_line_ranges` and `characters_added` / `characters_deleted`. This is NOT the same as `git diff`. We are measuring what the user types in the editor, not what gets committed.
- A `text_change` that adds and deletes within the same range counts on **both** sides (it's an in-place edit, and "rewriting a function is churn" is the intent).
- The ratio is clamped to `[0, 1]`. A range with no writing returns `ratio: null` (distinct from `0`).

### Context switching (`editor-switch-count`)

`switch_count` = number of `editor_switch` events in the date range.

The response also returns:
- `rapid_switch_count` — the subset flagged by the extension's `is_rapid_context_switching` heuristic.
- `top_files` — the most-visited destination file paths (`metadata.to.file`) in the range, ranked by count, capped at the requested `top_n` (max 20).

## Endpoints

All under `/api/v1`, JWT-protected (cookies or `Authorization: Bearer <jwt>`).

```bash
# Churn for a date range, daily grain (default)
curl -s "http://localhost:3000/api/v1/metrics/churn?from=2026-05-01&to=2026-05-13" \
     -H "Authorization: Bearer $JWT"
# → { "ratio": 0.42, "total_lines_added": 1200, "total_lines_deleted": 504,
#     "definition": "typing-heuristic", "from": "...", "to": "...", "grain": "daily" }

# Churn per session in a date range
curl -s "http://localhost:3000/api/v1/metrics/churn?from=2026-05-01&to=2026-05-13&grain=session" \
     -H "Authorization: Bearer $JWT"
# → { "sessions": [...], "definition": "typing-heuristic", ... }

# Context switching with top 5 files
curl -s "http://localhost:3000/api/v1/metrics/context-switching?from=2026-05-01&to=2026-05-13&top_n=5" \
     -H "Authorization: Bearer $JWT"
# → { "switch_count": 87, "rapid_switch_count": 12,
#     "top_files": [{ "path": "src/app.ts", "count": 22 }, ...],
#     "definition": "editor-switch-count", ... }
```

`grain` accepts `daily` (default) or `session`. `top_n` is a 1–20 integer (default 10).

## ETL — how the aggregates are produced

The periodic job [src/services/metrics-etl-scheduler.js](../src/services/metrics-etl-scheduler.js) ticks every `METRICS_ETL_INTERVAL_SECONDS` (code default 300, production runs at 60 — the dashboard's refresh timer is matched to this). On each tick:

1. Reads up to `METRICS_ETL_BATCH_SIZE` (default 5000) new `activities` rows since the watermark stored in `etl_jobs.last_processed_activity_id`.
2. Filters to `text_change` and `editor_switch` events; ignores all others (but still advances the watermark past them).
3. Upserts increments into `metrics_daily` keyed on `(user_id, date)` and `metrics_session` keyed on `session_id`.
4. Advances the watermark in the same transaction. A crash before commit rolls back the increments AND leaves the watermark in place, so the next pass redoes the same range and produces the same numbers (idempotent).

A `setInterval`-based in-process mutex prevents overlapping passes. If a tick fires while a pass is still running, it skips.

## Manual trigger (admin only)

```bash
curl -s -X POST http://localhost:3000/api/v1/metrics/etl/run \
     -H "Authorization: Bearer $JWT" -w '\n%{http_code}\n'
```

- Requires JWT auth (not an API token).
- The caller's `user.id` must be in the `ADMIN_USER_IDS` env var (comma-separated UUIDs).
- Returns `200` with `{ processed_count, watermark_before, watermark_after, duration_ms }`.
- Returns `409` if a pass is already in flight.

## First-time setup

The three tables (`etl_jobs`, `metrics_daily`, `metrics_session`) and the initial watermark row need to be created once:

```bash
node src/bootstrap-metrics-tables.js
```

This uses `sequelize.sync()` (no `force: true`) so it will NOT touch existing tables. It only creates what's missing.

## Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `METRICS_ETL_INTERVAL_SECONDS` | `300` | Seconds between scheduler ticks. Set to `60` in the cluster Secret so the dashboard's 60s auto-refresh sees fresh aggregates. |
| `METRICS_ETL_BATCH_SIZE` | `5000` | Max `activities` rows consumed per pass. |
| `METRICS_ETL_ENABLED` | `true` | Set to `false` or `0` to disable the scheduler (useful for tests / local debugging). |
| `ADMIN_USER_IDS` | _(empty)_ | Comma-separated UUIDs allowed to call `POST /metrics/etl/run`. |

## Sessions

A session is a logical block of coding activity, identified by a `session_id` UUID generated by the extension. One VS Code window can produce multiple sessions in a day; the extension rotates the `session_id` in three cases:

- **Idle-cap (automatic).** If no event has been recorded for `devvitalAI.idleSessionTimeoutMinutes` minutes (default 30), the next event after that gap starts a fresh session. The check is lazy — it runs on the next event, not on a background timer, so an idle laptop with VS Code open consumes no CPU.
- **`DevVital AI: Start New Session` (manual).** Forces a rotation immediately. Use this to deliberately chunk your day ("morning deep work" vs "afternoon meetings").
- **`DevVital AI: End Session` (manual).** Same effect as Start New Session, but framed as closing the current block. The next event opens a fresh session.

On every rotation the extension's in-memory aggregates (`active_minutes`, `idle_minutes`, `total_events_collected`, `save_frequency`, `editor_switch_frequency`) reset to zero, so each session's metrics reflect only its own events. The backend creates a new `Session` row the first time it sees a new `session_id`; previous sessions are left untouched.

### What this means for `metrics_session`

`metrics_session` is keyed on `session_id`, so multiple sessions per day per user is normal and expected. The metrics ETL doesn't merge them. The dashboard can present per-session views ("here's what your deep-work blocks looked like") alongside the calendar-day rollup from `metrics_daily`.

### Configuration

| Setting | Default | Purpose |
| --- | --- | --- |
| `devvitalAI.idleSessionTimeoutMinutes` | `30` | Minutes of inactivity before automatic session rotation. Minimum `1`. Changes take effect on the next idle check — no window reload needed. |

## Known limitations

- Heuristic line counts will diverge from `git diff`. This is expected — the metric reflects typing behavior.
- A `text_change` event without `affected_line_ranges` contributes zero to both counters and emits a warning to logs.
- `metrics_session` rows grow unboundedly. At ~10 sessions/user/day that's ~3.6k rows/user/year — fine for v1. If it gets unwieldy, prune sessions older than N months (won't affect `metrics_daily`).
- The scheduler is in-process and single-instance. Multi-replica deployment would need an advisory lock or extraction into a separate worker.
